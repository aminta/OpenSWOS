# AI development guidelines for the competition engine

> **Sintesi (IT).** Come devono lavorare le sessioni AI nel nuovo progetto: prima l'architettura e
> la spec, poi i test, solo dopo il codice; PR piccole e revisionate da un umano; niente patch di
> binari né reverse engineering "a caso"; tutto deterministico; documentazione aggiornata nello
> stesso commit del codice; appunti di contesto in `ai-notes/` per non ricaricare tutto a ogni
> sessione.

Status: proposal, 2026-10-25. Applies to work on the competition engine and data packs
(`competition-engine-proposal.md`). OpenSWOS's own `.claude/CLAUDE.md` rules (both targets build,
panics are signals, typed structs, named-field saves) apply in full on top of these.

## 1. Order of work: architecture, spec, tests, code

1. **Find the contract first.** Every change starts from the schema, the API header or the
   design doc it touches. If the contract does not cover the change, the first PR changes the
   contract (doc + schema + validator), reviewed on its own.
2. **Write the test before the code**: a spec fragment + seed + expected output (golden file or
   unit assertion). A format rule is "done" only when a test fails without it.
3. **Then the code**, the smallest that makes the test pass, inside the module the architecture
   assigns to it (stage engine, tie-break evaluator, draw engine, link resolver ...). No
   per-country branches: a country's peculiarity is data, or a new *named* rule usable by every
   country.

## 2. Small, reviewed pull requests

- One concern per PR (a rule, a stage type, a data pack, a refactor). Target under ~400 changed
  lines of code; data packs may be larger but carry no code.
- Every PR states: what contract it implements, which tests prove it, which golden files changed
  and why. A golden file never changes "by accident".
- A human reviews and merges. AI sessions never push to shared branches, never merge, never open
  upstream PRs or issues without the maintainer's explicit ok in that session.

## 3. No binary patching, no unbounded reverse engineering

- The engine is written from its spec, in C, in the source tree. No hex patches, no code caves,
  no byte-offset access to structures, no "this label is the next label" tricks.
- Reverse engineering of the original game is allowed only as **bounded research** with a
  question and a written answer: "what tie-breakers did the 1996 game use?" -> a note with the
  `SWOS2.s` / `swos.asm` references, then a spec. The faithful port remains the reference for
  original behaviour; the new engine never imitates a byte layout.
- Real-world formats come from cited sources (regulations, federation documents, Wikipedia pages
  with their revision), recorded beside the data.

## 4. Determinism is a hard rule

- No clock, no `rand()`, no floats in decisions, no iteration over unordered containers or
  pointer order. Randomness only through the engine's RNG with a named purpose (substream).
- Same specs + same seed + same results = byte-identical season output, on every target (SDL
  32/64-bit, Amiga). CI runs the golden harness on at least two targets.
- Result-dependent behaviour is tested by **forcing** results through the stub provider, never by
  re-running with different seeds hoping for the case (the Mod's rule, CONVENTIONS 15).

## 5. Documentation in sync

- A change to behaviour updates, in the same commit: the schema or API doc, the user-facing rule
  text (generated by `swc-explain` where possible), and the changelog. Documents for developers
  live in `docs/`; working notes for AI sessions live in `ai-notes/` and never replace `docs/`.
- New terms are defined at first use. Each doc has a dated status line (OpenSWOS's `docs/INDEX.md`
  convention) and is listed in `docs/INDEX.md`.

## 6. Context discipline for AI sessions

- Start from `ai-notes/README.md`: it lists the current state, the decisions taken and the open
  questions in a few hundred lines, so a session does not re-read the code base.
- Read code selectively (grep, targeted reads); record any new fact worth keeping as a line in
  `ai-notes/` with its `path:line` and the commit it was true at.
- At the end of a work block, update `ai-notes/` (state, next step) before stopping, so the next
  session resumes from the note and not from the transcript.

## 7. Definition of done (checklist for every PR)

- [ ] Contract (schema / API / doc) covers the change, updated in this PR if needed
- [ ] Validator accepts the new data and rejects a broken example (test included)
- [ ] Unit tests + golden files pass on SDL and Amiga builds; changed goldens explained
- [ ] No new hard-coded country, competition or club in engine code
- [ ] No floats, clock or unordered iteration in decision paths
- [ ] Docs (`docs/`) and notes (`ai-notes/`) updated; new doc listed in `docs/INDEX.md`
- [ ] Licence and source of any new data recorded in the pack's credits file
